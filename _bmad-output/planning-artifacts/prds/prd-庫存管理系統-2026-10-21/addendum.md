### 1.2 選型理由與取捨

- **React 而非純 HTML/CSS/JS**：本系統的畫面是「多品項 + 即時試算 + 表格過濾」，屬狀態密集型；React 的單向資料流讓「折扣變更 → 折後金額與毛利即時重算」（FR-16、FR-17）得以實作，而非靠手動重繪 DOM。React 的元件模型亦對應 MVVM：View = JSX、ViewModel = state 與 hooks、Model = Flask API。
- **PostgreSQL 而非 SQLite**：需要交易（FR-13 盤點、FR-11 移轉、FR-15 防止超賣的列鎖）、多使用者並行與稽核軌跡；SQLite 在課程環境的併發寫入容易出現鎖等待。
- **PostgreSQL 而非 MySQL**：兩者皆可；PostgreSQL 的交易隔離與 `SERIAL`／`BIGSERIAL` 流水號較貼合 FR-4 商品編號、FR-5 批次編號與各單據流水號需求。
- **Flask-Migrate 而非手動建表**：資料模型會隨 PRD 定案持續變動（批次與入庫單拆分、寄貨單與反向單據新增、權限矩陣落地）。migrations 讓「改了 schema」與「改了程式碼」走同一個版控流程，且可 `downgrade` 回退——這是課程專題在評分前調整資料模型的必需品。
- **REST + 單據狀態機**：FR-11 調貨單（草稿 → 在途 → 已收貨）、FR-23 採購單（草稿 → 已送出 → 部分入庫 → 已入庫）、FR-28 寄貨單（寄出 → 已收回／已轉銷貨）需要明確的狀態機，不建議讓前端直接改單據欄位。過帳後不可修改，後果以反向單據處理（FR-29）。
- **成本評價法只做一種並凍結**：研究顯示批次別評價在開源方案中時常有實作缺陷（ERPNext 批次評價 bug），且移動平均與 FIFO 混用會讓毛利計算無法對帳。v1 採 FIFO 並凍結（PRD A4）。
- **資料庫範圍原則**：單一專案對應單一資料庫（one project → one database），資料庫內以多張表承載各功能模組；不跨專案共用資料庫，也不在同一資料庫內切分多個應用 schema。此原則同時決定備份粒度與連線字串策略。

### 1.3 被拒絕的替代方案

| 方案 | 為何不選 |
| --- | --- |
| **純前端 + 直連資料庫**（簡報投影片 5 的簡化架構，無後端層） | 需在瀏覽器暴露資料庫連線與憑證，違反 PRD §4.8 資安與 FR-1；且無法落實 FR-2 權限矩陣與 FR-3 操作紀錄。本專案維持前後端分離。 |
| 直接採購現成進銷存 SaaS（鼎新、雲端方案等） | 課程目標是做出自己的系統；研究也指出小公司導入門檻在成本與學習，不在功能缺口。 |
| 以 Excel / Google Sheets 為主要介面 | 缺多倉庫、批次、權限與稽核軌跡；本研究列出的常見失敗模式（帳實不符、權限過寬）多由此產生。 |
| Odoo / ERPNext 等開源 ERP 直接架設 | 功能過重、學習曲線陡；且 Odoo 預設允許負庫存，正好踩中本研究列出的失敗模式。 |
| 採用 Odoo 的 Transit Location 調撥模型 | 作為**設計參考**採用（來源倉 → 在途 → 目的地倉），但 v1 自行實作以維持可控範圍。 |
| 手動建表（`CREATE TABLE` 腳本或 pgAdmin 手動建） | schema 會隨 PRD 定案持續變動，無版控即無法回溯與重現；改採 Flask-Migrate。 |
| Node.js / Go 後端 | 與 Flask 同為候選；選 Flask 的理由是教學熟悉度、與 Flask-Migrate 同源、與 PostgreSQL 整合直接。 |
| MySQL | 授權免費且教學多，但本專案所需之交易隔離與流水號特性 PostgreSQL 較貼合。 |
| SQL Server（msSQL） | 授權成本與課程環境可用性較差，且以 PostgreSQL 為主選時無額外價值。 |
| MongoDB | 本專案為強關聯（商品↔批次↔單據↔位置）＋交易需求，文件型資料庫不適用。 |
| 導入條碼／掃碼作為 v1 必要條件 | 需先確認既有標籤格式與編碼規則；列為 v2（PRD §6.2）。 |
| 權杖（token）與 AI 工具的自動化存取流程 | v1 保留觀念與最小權限原則即可，實際自動化流程列為 v2（PRD §5、§6.2）。 |

### 1.4 資料模型草稿與遷移策略

**資料庫**：`AILearn`（教學名稱；部署時由環境變數注入）。核心表：

| 群組 | 表 | 備註 |
| --- | --- | --- |
| 使用者 | `users`（帳號、密碼雜湊、角色、啟用狀態、首次登入旗標） | FR-1、FR-26 |
| | `roles` / `permissions` | v1 固定五種角色，權限可寫在程式碼或設定表；矩陣見 PRD §4.1 |
| 主檔 | `items`（`IT-` + 6 位流水、商品名稱、單位、建議售價、預估毛利率目標、狀態） | FR-4、FR-7 |
| | `suppliers`（統一編號、公司名稱、聯絡人、電話） | FR-20 |
| | `item_suppliers`（商品 × 供應商，多對多，含 `is_primary` 主供應商旗標） | FR-4、FR-20、FR-22 |
| | `customers`（客戶名稱唯一、聯絡人、電話、狀態） | FR-32 |
| | `warehouses`、`locations`（位置代碼 + 倉庫 FK） | FR-8 |
| 庫存 | `stock_ledger`（批次、位置、數量、正負號、異動類型、關聯單據、操作人員、時間） | **在手量的唯一來源**；位置可為實體位置或虛擬在途位置 |
| | `stock_balances`（批次 × 位置 的在手量快取） | 由 ledger 推導；**不含可用量** |
| | `allocations`（單據、批次、位置、數量、狀態） | **配置量**；**僅**銷貨單／寄貨單過帳時建立、領用時解除；**跨倉調貨不建配置**（移出即入在途）；可用量 = 在手量 − 配置量 |
| | `cost_consumptions`（單據行、批次、數量、單價、金額） | **成本取用明細**；FIFO 正確性與 FR-17 成本展開的基礎 |
| 單據 | `purchase_orders`、`purchase_order_lines`（PO 號、預估單價、總價、訂購數量、狀態） | FR-23 |
| | `grn`、`grn_lines`（GR 號、實際單價、數量、位置、批次 FK） | FR-9、FR-27 |
| | `batches`（`B-YYYYMMDD-NNN`、商品、來源 PO、實際單價、數量、入庫日期、有效期限） | FR-5，入庫時建立 |
| | `sales_orders`、`sales_order_lines`（SO 號、客戶 FK、數量、單價、折扣、折後金額、**成本快照**） | FR-14、FR-16、FR-17 |
| | `shipping_orders`（SH 號、客戶 FK、數量、狀態、經辦人） | FR-28 |
| | `transfer_orders`、`transfer_order_lines`（TO 號、來源／目的地倉、批次、數量、狀態、需求來源） | FR-11、FR-18 |
| | `returns`（RT 號、原單據 FK、數量、原因、回補批次） | FR-29 |
| | `stock_adjustments`、`stock_adjustment_lines`（AD 號、調整類型、批次、數量、原因、核准狀態） | FR-30、FR-31 |
| | `stocktakes`、`stocktake_lines`（盤點、基準時點、凍結狀態、實盤量、差異、原因） | FR-13 |
| 稽核 | `audit_log`（操作人員、時間、動作、單據／批次、數量、位置、原因） | FR-3，不可刪除 |
| 水位 | `reorder_points`（商品 × 倉庫、水位、交期天數、最小下單量、包裝倍數） | FR-21、FR-22 |

**設計重點：** 這是 v3 修訂後的模型，修正了 v1／v2 的三個結構性缺陷：
1. **在手量**由 `stock_ledger` 推導；**可用量**由「在手量 − `allocations` 配置量」推導。v2 把可用量放進 `stock_balances` 卻宣稱「餘額一律由 ledger 推導」，兩者互相矛盾——可用量在定義上無法由 ledger 推導，因為 ledger 只記實體異動、不記佔用。
2. **在途**是 `locations` 中的一筆**虛擬位置**（代碼 `TRANSIT`），因此「Σ所有位置餘額（含在途）= Σ入庫 − Σ出庫 + Σ盤盈 − Σ盤虧」恆等式在轉運期間仍成立（PRD FR-24、SM-3）。
3. **`cost_consumptions` 必須存在**，否則 FR-17 的逐批成本展開與 FIFO 可稽核性無從實作。

**其他實作要點**
- `stock_balances` 為快取，任何寫入後可由 ledger 前綴和重建；建議將此重建查詢作為開發期自我檢查工具（PRD SM-3 建議）。
- **盤點凍結**：盤點進行中，該範圍的庫存寫入以應用層檢查（凍結旗標）阻擋，不靠 DB 約束。
- 數量型別：若支援小數（如 0.5 kg），統一小數點後 3 位四捨五入；v1 預設整數 [ASSUMPTION: A16]。

**遷移策略（Flask-Migrate）**
- 遷移檔案納入版控，命名附語意（`create items`、`split batch from grn`、`add shipping_orders`），禁止「一次性大改表」。
- **模型變更與 PRD 定案同步**：PRD 的 D2（批次於入庫時建立）即對應一組 migration，而非事後手改。
- 測試與開發使用同一組 migration 重建資料庫，確保「乾淨重現」。
- 種子資料（基礎角色、五種權限、示範倉庫與位置）以 migration 或 seed 腳本一併建立。

## 2. 市場與競品研究摘要

完整 digest 見 `research-market.md`。對 PRD 的主要影響：

- **可比基準**：Zoho Inventory 的免費層功能清單被視為 v1 功能基準的參考；Odoo、ERPNext、NetSuite、Dynamics 365 SCM、Infor WMS 各自提供了可借鑑的模組（批次追溯、防止負庫存、Transit 調撥、min/max 補貨、Auto Hold 過期批次）。
- **補進 PRD 的概念**：**在手量 vs 可用量**（FR-6、FR-15、FR-21、FR-22 一律依可用量判斷）、**在途量**（FR-11、FR-18）、**盤點差異需有原因**（FR-13）、**單據狀態機不可直接改過帳**（FR-14、FR-23、FR-29）、**建議售價反推**（FR-7）。
- **刻意未納入（列為 v2 或 addendum）**：條碼、ABC 分類、循環盤點、到期批次 Auto Hold、總成本分攤（landed cost）、自動補貨。
- **本研究點名的失敗模式，PRD 對應的緩解措施**：
  1. 帳實不符（shrinkage）→ FR-13 盤點、FR-3 稽核軌跡、SM-3 帳面等式、SM-4 實盤抽樣準確率。
  2. 負庫存／超賣 → FR-10、FR-15、FR-18 的可用量阻擋＋列鎖。
  3. 成本評價錯誤 → FR-5、FR-17 成本可展開檢視、SM-5 毛利正確率；A4 凍結單一評價法；D3 成本取實際入庫單價。
  4. 權限過寬 → FR-2 權限矩陣、FR-26 帳號管理、SM-7 越權測試。
  5. 多倉在途遺失 → FR-11 調貨兩段式（在途不計入任一倉可用量）、FR-18。
- **本研究指出的「容易漏掉但重要」項目**：費用未攤提導致毛利虛高（PRD §6.2 標為 `[NOTE FOR PM]`）、單據狀態機與不可直接改過帳（已納入 FR-14、FR-23、FR-29）。

## 3. AI 協作開發與憑證處理原則

簡報投影片 8 提出「AI 沒有資料庫登入密碼，因此將密碼寫在文本中讓 AI 拿文本去開鎖」。這是**教學便利**與**安全原則**的衝突，本專案採以下原則（並已在 PRD §3「帳密」與 §4.8 資安要求落地）：

1. **明文密碼不進版本控制、不進投影片、不進對話紀錄、不進日誌。** 示範時以佔位符或遮蔽呈現。
2. **需要讓外部工具（含 AI 輔助工具）存取資料庫時**，建立**最小權限的獨立帳號**，權限只限於必要 schema 與必要操作，設定到期時間並可隨時撤銷；連線字串透過環境變數或本機私密設定檔注入，不進原始碼。
3. **資料庫密碼於後端以環境變數讀取**，開發用 `.env` 檔案加入 `.gitignore`；示範與作業環境分離。
4. **在產出物中說明這些原則本身**是本課程的安全學習成果之一：示範流程可以示範「如何安全地給工具存取權限」，而非「如何繞過」。
5. 依 PRD SM-C2，AI 生成的程式碼須經人為審查與驗證後才計入完成度。

### 3.3 連線字串與環境變數

`DATABASE_URL`（含 `postgresql://<user>:<password>@<host>:5432/AILearn`）以環境變數注入，後端由 `Flask-SQLAlchemy` 讀取；`.env` 不進版控（`.gitignore` 至少含 `.env`、`instance/`、`__pycache__/`、`.venv/`）。

### 3.6 教學展示流程（對應簡報投影片 8）

- **Step 1（建立資料庫）**：由具**最小權限帳號**（僅 `CREATEDB`）的示範流程建立目標資料庫 `AILearn`；該帳號與後端讀寫用的資料庫帳號**分離**。若由 AI 輔助工具執行，僅授予 `CREATEDB` 而非 `SUPERUSER`。
- **Step 2（開鎖與存取）**：以**佔位符或遮蔽後的憑證**示範「工具需要存取權限」這件事本身，重點在說明**為何不交明文**、以及最小權限與可撤銷的作法；不真的把明文密碼交給任何工具。
- **Step 3（Schema）**：以 dbdiagram.io 產出 ER 圖，再轉為 Flask-Migrate 的 migration 檔案，示範「設計 → 遷移 → 可重現」的工作流。
- **Step 4（示範檢視）**：以 pgAdmin 連線查看資料表與資料，佐證 migration 與種子資料已就位。

## 4. 課程情境下的範圍控管紀錄

- 依 PRD §6.1，v1 聚焦「商品 → 單據 → 餘額 → 成本 → 毛利」主線。
- 依 PRD §6.2，條碼、行動 App、離線、自動補貨、**可自訂權限組合**、總成本分攤、線上審核、通知、權杖自動化皆移出 v1；其中**總成本分攤**若課程要求毛利精確度，需重新評估。**客戶主檔已納入 v1**（PRD FR-32，僅「客戶名稱／聯絡人／電話」三欄位），非移出項目。
- 依 PRD §5，v1 明確不做 POS、電商串接、製造、Multi-company、多幣別與行動原生 App。
- 依 PRD §7，評分準則以覆蓋率、情境可演示、帳面等式、實盤準確率、毛利正確五項為主，並以 SM-C1 防止以功能數量灌水。
- **加值項標記**：盤點（FR-13、UJ-7）與報表（FR-24、FR-25、UJ-6）為研究導向的加值，簡報未要求；若課程評分只看簡報覆蓋率，此二項為純成本，應依 PRD §6.2 的降級路徑處理（盤點降為差異登記、報表收斂為三張固定表格 + CSV）。
