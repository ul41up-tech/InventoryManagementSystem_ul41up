## 3. 明確缺口（Gaps）— 必須處理

### G-1（技術／課程規則）「一個專案一個 DataBase、一個 DataBase 多個表」未落文
- **來源**：slide6 兩行明文。
- **現況**：PRD 完全未提；Addendum §1.4 只以「核心表清單」隱含，PRD §5 甚至寫「不做多公司／多組織」但未說明「單一專案＝單一資料庫」這條基礎邊界。這條規則同時決定未來是否需要 schema 隔離、備份粒度與連線字串策略，架構階段會直接撞到。
- **建議**：在 Addendum §1.4 開頭加一段「資料庫範圍原則」：*「本專案採單一專案對應單一資料庫（one project → one database）；資料庫內以多張表承載各功能模組，不使用跨專案共用資料庫，也不在同一資料庫內切分多個應用 schema。」*，並在 PRD §4.7 資料完整性條目補一句「所有資料表同屬單一專案資料庫」。**（低成本、高價值，強烈建議立即補）**

### G-2（教學流程）`AILearn` 資料庫名稱與「Step1 由 AI 新增 Database」步驟遺失
- **來源**：slide8 Step1。
- **現況**：Addendum §3 只保留了 Step2 的「憑證處理原則」，完全沒有落實 Step1 的動作與結果物（資料庫名稱）。同時 PRD 也沒有任何一條需求描述「AI 輔助工具依授權建立目標資料庫」這個課程展示步驟。
- **建議**：(1) 在 Addendum §1.1 表格或 §1.4 開頭明定**本專案資料庫名稱為 `AILearn`**（或註明「教學專用，實際部署時改為環境變數注入」）；(2) 在 Addendum §3 新增第 6 點：「教學展示流程 Step1：由具最小權限帳號的 AI 輔助工具建立目標資料庫 `AILearn`（僅 CREATE DATABASE 權限，與讀寫帳號分離）；Step2：以佔位符／遮蔽後的憑證交付示範，重點說明為何不交明文。」

### G-3（架構變體）slide5 的「前端 + 資料庫（無後端層）」簡化架構未被記錄
- **來源**：slide5 與 slide4 並列，前者無「後端」列，且列出的 SQL 與投影片 4 一致。
- **現況**：Addendum §1.1 只承諾三層分離架構，PRD §9 A3 也直接凍結 Flask + PostgreSQL。若授課者要求的是 slide5 這種簡化版本，PRD/Addendum 將與簡報互相矛盾且無退路。
- **建議**：在 Addendum §1.3「被拒絕的替代方案」加一列：「**純前端 + 直連資料庫（簡報投影片 5 的簡化架構）** — 不選：需在瀏覽器暴露資料庫連線與憑證，違反 §4.7 資安與 FR-1；亦無法落實 FR-2 角色權限與 FR-3 操作紀錄，故本專案維持前後端分離。」→ 把它變成「已評估並拒絕」的紀錄，而非遺漏。

### G-4（候選技術盤點不完整）msSQL 與 MongoDB 未列入取捨；pgAdmin 未成為明文工具
- **來源**：slide4 資料庫列（MySQL / pgSQL / msSQL / SQLite）、slide7（PostgreSQL / pgAdmin / mySQL / SQLite / MongoDB）。
- **現況**：Addendum §1.2 只解釋了 MySQL 與 SQLite 為何不選；msSQL 與 MongoDB 完全消失。pgAdmin 只在 §1.1 表格欄位出現一次。
- **建議**：(1) §1.2 補兩列：msSQL（授權成本與課程環境可用性）、MongoDB（本專案為強關聯＋交易需求，文件型資料庫不適用）；(2) 在 §1.1 表格或新增 §1.5「工具鏈」明列 **pgAdmin 為本專案指定的 DB 管理／ER 檢視工具**，與 dbdiagram.io（設計）分工。

### G-5（輕微）商品層級「採購日期」無落點
- **來源**：slide11「每個商品需要紀錄…採購日期」。
- **現況**：只由批次進貨日期與 PO 預計到貨日期分攤承載，商品查詢結果（FR-6／FR-12）看不到採購日期。
- **建議**：FR-6 後果增一條：「結果顯示最近一次採購日期（取該商品最新批次的進貨日期）。」

## 4. 部分缺口（Partially Covered）— 建議補強

### G-6「快速搭配多項商品」的「快速」機制缺失
- FR-14 僅要求「加入多項商品」，沒有任何「快速」的可驗證行為。簡報原文「快速搭配多項商品」在中文語境更接近「快速搭配／一次挑多種商品」的組裝需求。
- **建議**：FR-14 後果增補兩條可驗證條款：
  - 「可由商品查詢結果（FR-6／FR-12）多選後一次加入同一張銷貨單，加入時自動帶入各倉可用量並標示缺口。」
  - 「提供常用組合（商品組）快速套用功能：可將一組商品儲存為組合並於新銷貨單一鍵帶入 [ASSUMPTION]。」

### G-7「客戶寄貨」只到 FR-10 為止，寄貨紀錄無主檔、無對象、無回收
- 簡報把「客戶寄貨」與「銷貨」並列為領用用途，暗示它是獨立業務流程。PRD 只有 FR-10 一條後果提到「寄貨紀錄」，沒有：寄貨對象（客戶）欄位、寄貨單狀態、寄回（回收）流程、寄貨佔用可用量的處理、寄貨報表。
- **建議**：至少在 PRD 明確定調並升級為正式 FR 或明確降級：
  - 方案 A（推薦）：新增 FR-10a「客戶寄貨」：寄貨單含寄貨對象（自由文字或客戶主檔）、數量、日期、經辦人、狀態（寄出／已收回／已轉銷貨）；寄出期間計入可用量扣減、不得重複出貨。
  - 方案 B（保守）：在 FR-10 補明「v1 寄貨僅記錄『用途＝客戶寄貨』的領用紀錄，不含寄回與寄貨對象管理」，並在 §6.2 明列寄回流程為 v2。
  - 目前狀態最糟：FR-10 提到「寄貨紀錄」但全文件沒有它的資料結構，容易在開發中變成無主孤兒。

### G-8「輸入位置，針對該位置放入某物品」缺獨立條目
- 見 §2.4 V7。
- **建議**：在 §4.3 新增 FR-9a「以位置為入口的入庫」：輸入位置代碼 → 顯示該位置現有品項與空位 → 對指定品項輸入入庫數量完成入庫；後果：「位置代碼不存在的組合被拒絕並提示可用位置清單」「同一位置同一品項重複入庫需合併或另建紀錄」。或在 FR-9 後果補一條以涵蓋。

## 8. 整體評語

PRD 在**業務需求層**的覆蓋品質很高：slide10 ~ slide14 的每一條實質需求（人員四職能、商品編號自動流水、位置／數量／供應商／採購日期／批次／單價／批次數量、進出庫與銷貨的操作紀錄、銷售的查貨／多品項／折扣／毛利／建議售價／調貨單、庫存的快速定位／入庫領用／移轉／用途／多倉庫、採購的水位／警示清單／供應商四欄位／批次流水號／總價／單價）幾乎都能一對一對應到具備可驗證後果的 FR，這是簡報中斷言式、需要被推導成驗收條件的部分，做得好。

問題集中在**技術與教學層**：PRD 刻意把技術移到 addendum 是合理的，但 addendum 在「把簡報當課程教材」這個維度上仍有三處失守——**資料庫邊界規則（one project one DB）、兩步驟 AI 建庫教學（含 AILearn 命名）、簡化架構變體**都沒有留下文字痕跡。這三項在下游架構／開發／簡報演練時會被重新發現，而且每次發現都要回頭翻簡報。

另外必須講明：**PRD 有兩塊成本高於簡報要求的加值（盤點 FR-13、四張報表 FR-24/25）**，它們來自市場研究而非本簡報，若課程評分只看簡報覆蓋率，這兩塊是純成本；建議降級或明示為加值項，而非混在 v1 必交清單裡。
